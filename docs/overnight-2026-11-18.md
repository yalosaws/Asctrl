### 动画分析与重新设计（前后数字）

方法：每个桌面测试都设 `ASCTRL_FX_LOG` 录下驱动发给 overlay 的事件，用 `test/fxcheck.ts` 在无界面 Chrome 里用 overlay 的真实代码按原时间重放，记录每一帧球的位置和形状、每个指针的出现/消失/按下、每个框的出现/消失，再算指标；`test/zorder.ps1` 每毫秒采样窗口顺序，算 overlay 被盖住的时间。

| 指标（p4） | 改之前 | 只改 frameFor（上一轮的假设） | 现在 |
|---|---|---|---|
| 球在同一程序里的多余移动 | 10 | 2 | 0 |
| 框（同一窗口里重画） | 10 | 1 | 1（不重画） |
| overlay 被测试窗口盖住 | 9 次 / 1675 ms / 最长 279 ms | 同左 | 工作中 1 次 / 3 ms |
| 网页通道点击没画任何东西 | 3 | 3 | 0 |

| 其他测试 | 改之前（第一版"按窗口记框"） | 现在 |
|---|---|---|
| p2（主窗口和它的对话框来回） | 球移动 6 | 2 |
| p6（两个程序并行） | 球移动 11、框 14、没画出的按下 3、最慢滞后 959 ms | 4、5、0、588 ms |
| run / l2 / l4 / p4b | 同一窗口里重画框 4 / 2 / 1 / 1 | 0 / 0 / 0 / 0 |
| 所有测试的录像 | 8 个超限 | 0 个超限 |

两个假设的结论：pointer.rs 那一版（click 也框控件组）确实会更糟（点击的目标可能不在控件组里），已撤销的做法是对的；fx.ts frameFor 的"同一窗口换个切法就保留旧框"方向对，但只靠矩形包含关系猜，遇到对话框、两个窗口并行就失效，所以改成由驱动直接说明"哪个窗口、哪个程序"。

设计原则（都能被 fxcheck 量到）：球只在换程序时移动；同一窗口的框只画一次；指针按列分工、每个窗口一组；动画从不拖住动作（所有等待都在动画这边，按下最多晚半秒，落后时自动加速）；窗口关闭/隐藏/移动时框立即消失（leftovers 指标全为 0）。

### 仍然存在的限制（和原因）

- **管理员程序的窗口在最前时**，非管理员的驱动无法切换窗口或输入（Windows 的 UIPI 安全边界，任何 API 都不行）。驱动现在会明确说是哪个程序挡着，`observe` 仍可用；要越过它只能 `request_admin`（需要人点"允许"和 UAC）。
- 路线图"还没做的"里这些今晚没做，原因见 `docs/architecture-v2.md` 第 5 节：
  - L0 世界模型重写（UIA 事件订阅的增量树、UIA 与 DOM 节点合并、用事件判断稳定）：风险最大，路线图定的前提是"P0 数字证明需要"；今晚 P0 是 39/40，失败不在感知层，数字不支持现在重写。
  - Office COM 通道：P0 的 Office 10/10 都是靠界面完成的，暂无必要。
  - 旧 `run` 计划编译成程序：两者共用批处理和恢复，收益小、回归风险大。
  - `exec` 立即返回+通知推送：现有 MCP 客户端（Claude Code）不把服务器通知交给模型，做了也用不上。
  - 驱动只回结构化数据：协议级改动，需要先和控制台、中继一起设计。
  - 检查点/撤销：没有通用的撤销手段；后置条件已有 `expect`（计划）和 `until`（程序）。
  - 程序卡住时的局部变量：QuickJS 绑定拿不到调用帧的局部变量；用 `ask(问题, 细节)` 交出。
- 窗口消息通道只做了按钮（BN_CLICKED）；其他控件仍走 UI Automation。
- "动作做到一半用户动鼠标"的保护没有自动化测试（需要在两次系统调用之间精确地插入人的移动），靠代码审查。
- overlay 看起来怎么样（颜色、弧度）仍要人眼判断；fxcheck 量的是位置、时间和出现/消失。
